# Multi-Step RAG Agent

## О проекте

Multi-Step RAG Agent - локальный многодокументный RAG-ассистент с гибридным поиском,
кросс-энкодерным реранкингом и агентом, вызывающим инструменты. Система отвечает на
вопросы по загруженным документам, указывает источники ответов. Агент различает сленг и
аббревиатуры компании и опирается на корпоративный словарь при генерации. Всё работает локально:
без внешних API и платных сервисов.

### Что делает система

Пользователь задаёт вопрос в командной строке (**agent.py**). LLM (qwen2.5:14b через Ollama) сама
решает, как отвечать: напрямую, поиском в базе знаний или вызовом инструмента.
Если нужен поиск, запускается retrieval, найденные чанки передаются модели
как контекст, и агент формулирует ответ. Система обязательно выводит строку
«Источники: ...» - для того, чтобы было видно, из какого файла пришёл ответ. Диалог сохраняется в историю
и переживает перезапуск программы.

### Как работает

**1. `ingest.py`**
- Читает все `.txt`-файлы из `data/`.
- Адаптивный чанкинг: текст режется по предложениям и абзацам, а не по символам —
  обычное предложение никогда не разбивается, граница абзаца становится естественным
  разрывом чанка. Заголовки разделов (`## ...` или короткая строка-название) не теряются:
  каждый чанк несёт заголовок своего раздела.
- Строит dense-эмбеддинги чанков моделью `BAAI/bge-m3` и сохраняет их в ChromaDB
  с метрикой cosine.

**2. `retrieval.py`**
- Трёхканальный поиск:
  - Семантика: ближайшие чанки по косинусному сходству dense-эмбеддингов `BAAI/bge-m3` в ChromaDB.
  - Learned-лексика: SPLADE-подобный скоринг по sparse-весам BGE-M3 (`Σ q_i·d_i` по пересечению
    токенов) — ловит точные термины и имена.
  - Okapi BM25 на леммах (pymorphy3): точная лексика словоформ, дополняет learned-sparse.
- Взвешенный Reciprocal Rank Fusion: `score(doc) = Σ w·1/(60 + rank)` по трём ранжированиям.
  Веса dense/sparse и `top_k` (число чанков в контекст LLM) система **подбирает сама**:
  `ingest.py`/`POST /reindex` считают отпечаток `data/*.txt` и, если документы изменились,
  запускают grid-search по eval-набору (`docs/eval_questions.json`), лучший конфиг сохраняется
  в `chromadb/retrieval_tuning.json` (том, переживает рестарт) и применяется при старте.
  Дефолты (dense 1.0, sparse 0.8, top_k 3) — эвристики до первого автоподбора.
  Человеку не нужно трогать веса: достаточно обновить документы. Ручной полный подбор —
  `python retrieval.py --tune`.
- Опциональный реранкинг: кросс-энкодер `BAAI/bge-reranker-v2-m3` переоценивает
  топ-20 кандидатов и возвращает точный топ-3.

**3. `agent.py`**
- Multi-step цикл: модель может вызывать инструменты несколько раз подряд, пока не
  ответит без вызовов; защита от зацикливания - `max_iterations`.
- Инструмент: `search_article` (гибридный поиск по базе знаний).
- Цитирование источников: retrieval возвращает чанки с полем `source` в метаданных,
  источники выводятся кодом, а не полагаются на надёжность модели.

**4. `main.py`**
- Интерактивный диалог в консоли; команды `/history`, `/clear`, `/quit`.
- История диалогов хранится в `history.json` между сессиями.

**5. `retrieval.py`**
- Eval-набор в `docs/eval_questions.json` (вопрос → ожидаемый источник).
- Recall@3 - доля вопросов, где нужный документ доставлен в топ-3 (то, что реально
  уходит в контекст LLM); MRR@3 - качество ранжирования внутри топ-3; NDCG@5 -
  позиционно-взвешенная метрика на глубине 5 (бинарная релевантность).
- Метрики доступны в `--tune --metric {mrr|recall|ndcg}` — можно оптимизировать
  веса под любой критерий.
- A/B-режимы: семантика vs гибрид, с реранкером и без.
- Авто-подбор параметров: система сама переподбирает веса при изменении документов
  (`ingest.py`/`POST /reindex`); ручной полный прогон — `python retrieval.py --tune`.

### Используемые модели

| Компонент | Решение |
| :--- | :--- |
| Эмбеддинги (dense + sparse) | `BAAI/bge-m3` (`FlagEmbedding`) |
| Лексика (3-й канал) | Okapi BM25 на леммах (pymorphy3), чистый Python |
| Реранкинг | `BAAI/bge-reranker-v2-m3` |
| Генерация | `qwen2.5:14b` (Ollama, локально) — меняется через `LLM_MODEL` |

Модель генерации настраивается переменными окружения (для Docker: `LLM_MODEL=... docker compose up --build`):

| Переменная | По умолчанию | Назначение |
| :--- | :--- | :--- |
| `LLM_MODEL` | `qwen2.5:14b` | Имя модели в Ollama (pull + healthcheck тоже используют её) |
| `LLM_NUM_CTX` | `8192` | Размер контекста; меньше → быстрее, но короче контекст RAG |
| `AGENT_MAX_ITERATIONS` | `3` | Максимум шагов цикла агента (в т.ч. повторных вызовов `search_article`) |
| `MAX_HISTORY_TURNS` | `6` | Сколько последних сообщений диалога уходит в контекст (структурный кап токенов) |
| `OLLAMA_MAX_RETRIES` | `3` | Повторы запроса к Ollama при транзиентных сбоях (догрузка модели, сеть) |
| `LLM_SELF_CHECK` | `0` | `1` — включить проверку «ответ подтверждён контекстом» (рекомендуется для моделей 7B+) |
| `OLLAMA_HOST` | `http://localhost:11434` | Адрес Ollama (в compose уже `http://ollama:11434`) |

> **Про выбор `qwen2.5:14b`:** лучшее соотношение качества русского текста, надёжности tool-calling и скорости на CPU в рамках ограничений (open-модель ≤40B). Дефолтный тег — `q4_K_M` (~9 ГБ). На очень слабых машинах опуститесь до `qwen2.5:7b` или `llama3.2` — код без изменений, достаточно `LLM_MODEL=`.

Скорость: при старте модель прогревается (не грузится с нуля на первый запрос жюри), а `keep_alive=-1` держит её в памяти между запросами — второй и последующие ответы в разы быстрее. Multi-hop: агент может вызвать `search_article` несколько раз с разными подзапросами (контекст и источники суммируются).
| Векторная БД | `ChromaDB` (cosine) |

## Структура проекта
* `data/` - директория для текстовых документов и баз знаний.
* `corporate_dictionary.json` - корпоративный словарь аббревиатур и терминов.
* `core.py` - чистые функции (чанкинг, лемматизация, RRF, распознавание сленга) без тяжёлых ML-зависимостей — их легко юнит-тестировать.
* `ingest.py` - скрипт загрузки, адаптивного чанкинга и индексации в ChromaDB (dense-эмбеддинги BGE-M3).
* `agent.py` - логика работы агента, распознавание сленга, цикл вызова инструментов.
* `retrieval.py` - модуль гибридного поиска на одной модели BGE-M3 (dense + sparse, взвешенный RRF) и оценки его качества.
* `app.py` - HTTP API на FastAPI (эндпоинты `/chat`, `/history`, `/reindex`, `/health`).
* `main.py` - точка входа для запуска диалога с агентом в консоли.
* `tests/` - юнит-тесты (`pytest tests/`).
* `docs/demo_cases.md` - сценарии для демонстрации жюри.
* `examples/` - готовые скрипты демо-прогона (`run_demo.sh`, `run_demo.ps1`).
* `Dockerfile`, `docker-compose.yml` - контейнерная сборка с предзагрузкой моделей.
* `requirements.txt` - список зависимостей проекта.

## Корпоративный словарь

Словарь аббревиатур лежит в `corporate_dictionary.json` в формате `"аббревиатура": "расшифровка"`:

```json
{
  "ГПН": "Газпром нефть",
  "ГПНР": "Газпромнефть-Развитие"
}
```

- Если файла нет или он битый, агент использует встроенный fallback-словарь (`agent.py`) — прототип не падает.
- При запросе каждый токен нечетко сопоставляется с ключами словаря (`rapidfuzz`): точное написание не шумит, а «гпнр», «ГПН-Р», опечатки вроде `КПЕ → КПЭ` распознаются автоматически (для аббревиатур порог мягче — 60%, для обычных слов — 80%).
- Токен приводится к каноническому виду: убираются разделители («ГПН-Р» → ГПНР) и заменяются визуальные омонимы латиница/кириллица («ГПН» с латинской H → ГПН).
- Работает **двунаправленная карта**:
  - прямая: «АЗС (автозаправочная станция)» — аббревиатура в запросе дополняется расшифровкой;
  - обратная: пользователь пишет «автозаправочная станция», а в документах только «АЗС» → система по леммам находит расшифровку в запросе и дописывает «(АЗС)», чтобы лексический поиск гарантированно нашёл документ с аббревиатурой. Падежи («ключевыми показателями эффективности» → КПЭ) покрываются лемматизацией pymorphy3.
- Расшифровки подставляются в system-промт (блок `<resolved_slang>`) и обогащают запрос для поиска, поэтому LLM обязана их учитывать в ответе.

## Запуск

### Локально

```bash
pip install -r requirements.txt
python ingest.py            # построение базы знаний из /data
python main.py              # диалог с агентом в консоли
```

Требуется установленный и запущенный **Ollama** с загруженной моделью `qwen2.5:14b`:
```bash
ollama pull qwen2.5:14b
```

### Тесты

```bash
pip install -r requirements.txt
pytest tests/ -q   # 16 тестов: чанкинг, лемматизация, RRF, распознавание сленга
```

Тесты не скачивают ML-модели — они покрывают только чистые функции из `core.py`.

### Docker (рекомендуемый способ)

```bash
docker compose up --build
```

Происходит автоматически:
1. Скачиваются HF-модели (эмбеддер + реранкер) и запекаются в образ.
2. Поднимается контейнер `ollama`, скачивается `qwen2.5:14b` (том `ollama_data`).
3. `ingest.py` строит базу знаний в ChromaDB (том `./chromadb`).
4. Стартует API на `http://localhost:8000`.

Повторные запуски быстрые: все модели уже в томах, база знаний не пересоздаётся.

Устойчивость: модели и база знаний инициализируются **лениво** — сервис не падает, если папки `./chromadb` ещё нет (на старте появится предупреждение, поиск вернёт пусто). После добавления документов в `data/` достаточно `POST /reindex`, перезапуск не нужен.

## HTTP API (FastAPI)

Swagger UI (OpenAPI-спецификация): `http://localhost:8000/docs`, схема: `http://localhost:8000/openapi.json`.

Готовые сценарии для демонстрации жюри (сленг, опечатки, отказы, мульти-терн): [`docs/demo_cases.md`](docs/demo_cases.md).

| Метод | Путь | Назначение |
| :--- | :--- | :--- |
| `POST` | `/chat` | Задать вопрос ассистенту |
| `GET` | `/history/{session_id}` | История диалога сессии |
| `DELETE` | `/history/{session_id}` | Очистить сессию |
| `POST` | `/reindex` | Перечитать документы из `data/` и перестроить индекс без перезапуска |
| `GET` | `/health` | Readiness: статус сервиса, Ollama, готовность базы знаний и моделей |

### Примеры запросов

```bash
# Основной запрос со сленгом (создаст новую сессию)
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"query": "Какая EBITDA у ГПНР за 2025 год?"}'

# Мульти-терный диалог: передаём session_id из предыдущего ответа
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"query": "А в 2024?","session_id": "ваш_session_id"}'

# Проверка статуса
curl http://localhost:8000/health

# История сессии
curl http://localhost:8000/history/ваш_session_id
```

Пример ответа `/chat`:

```json
{
  "session_id": "5f8b...",
  "answer": "По данным базы знаний... [Источник: article.txt]",
  "sources": ["article.txt"],
  "resolved_terms": [{"original": "ГПНР", "canonical": "Газпромнефть-Развитие", "score": 95.0}],
  "raw_context": "…",
  "latency_ms": 1240.5
}
```

Заметка: для автотестов жюри важно, что `/health` работает и через Docker — адрес Ollama берётся из `OLLAMA_HOST` (в compose: `http://ollama:11434`).

## Оценка качества поиска

Оценка качества поиска проводилась на тестовом наборе запросов с фиксированной глубиной выдачи $K=3$:

| Метод поиска | Recall@3 | MRR@3
| :--- | :--- | :--- |
| **Семантический поиск** | 0.92 | 0.821
| **Гибридный поиск (без реранкера, без лемм)** | 1.00 | 0.859
| **Гибридный поиск + BGE-M3(без лемм))** | 0.92 | 0.923
| **Гибридный поиск (без реранкера + лемматизация)** | 1.00 | 0.795
| **Гибридный поиск + BGE-M3 + лемматизация)** | **1.00** | **1.000**

## Результаты реранкинга

>Мультиязычный реранкер (BGE-M3) улучшил MRR@3 с 0.859 до 0.923 (+7.5%), но снизил Recall@3 с 1.00 до 0.92.  
**Вероятная причина:** агрессивное переупорядочивание на запросах с неточными формулировками. Для работы в реальных условиях рекомендуется A/B-тестирование обоих реранкеров на реальных пользовательских запросах.

## Результаты лемматизации

>Лемматизация ухудшила качество ранжирования без реранкера (MRR 0.859 -> 0.795), скорее всего из-за того, что разные чанки стали выглядеть похоже после приведения к леммам. Реранкер компенсировал это ухудшение: пара (query, doc) видна ему целиком и результат не зависит от токенизации.  
**Итог:** лемматизация + реранкер - это лучший результат, но без реранкера лемматизацию лучше не использовать.

## Известные ограничения (Known Limitations)
**Качество планирования на малых моделях:** Модели 3B иногда вызывают инструменты с некорректными параметрами или пропускают вызов `search_article`. Дефолт `qwen2.5:14b` заявлен как надёжный минимум; на слабом железе (`llama3.2`) возможны пропуски — включите `AGENT_MAX_ITERATIONS` повыше.

## Roadmap

### Приоритетные

1. **Обработка ошибок в инструментах (graceful degradation)**: при недоступности поиска агент должен отвечать понятным сообщением, а не падать с 503.
2. **YAML-конфиг**: вынести параметры чанкинга, retrieval и моделей в отдельный файл.
3. **BM25-канал**: уже добавлен (третий канал fusion, см. раздел retrival).
4. **Структурный чанкинг**: уже добавлен — `adaptive_chunk` держит заголовки разделов.

### Долгосрочные

5. **BGE-M3 multi-vector (ColBERT)**: включение третьего режима эмбеддингов для late-interaction скоринга — дальнейшее улучшение над текущим dense+sparse.
6. **Tracing (Langfuse/Phoenix)**: визуализация цепочек вызовов агента и метрик по шагам.
7. **NDCG@K с градацией релевантности**: сейчас NDCG@5 считается на бинарной релевантности (один источник на вопрос); наличии многоуровневых эталонов (0–3) метрика станет полноценной.
