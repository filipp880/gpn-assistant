# Multi-Step RAG Agent

## О проекте

Multi-Step RAG Agent - локальный многодокументный RAG-ассистент с гибридным поиском,
кросс-энкодерным реранкингом, декомпозицией запроса и agent-пайплайном. Система отвечает на
вопросы по загруженным документам, указывает источники ответов. Агент различает сленг и
аббревиатуры компании, разбивает сложные вопросы на подзапросы и опирается на корпоративный
словарь при генерации. Всё работает локально: без внешних API и платных сервисов.

### Что делает система

Пользователь задаёт вопрос через HTTP API (`app.py`) или в командной строке (`main.py`).
Пайплайн обработки запроса:

```
Запрос → resolve_slang (словарь + fuzzy) → декомпозиция (LLM) → параллельный поиск → синтез (LLM) → ответ
```

- **resolve_slang** — распознавание сленга/аббревиатур/опечаток через корпоративный словарь.
- **Декомпозиция** — сложный вопрос автоматически разбивается на 1-3 подзапроса.
- **Параллельный поиск** — подзапросы ищутся одновременно (ThreadPoolExecutor).
- **Синтез** — LLM формулирует единый ответ по объединённому контексту.
Система обязательно выводит источники ответов. Диалог сохраняется в Redis (с fallback на память)
и переживает перезапуск системы.

### Как работает

**1. `ingest.py`**
- Читает все `.txt`-файлы из `data/`.
- **Parent-Child чанкинг**: документ разбивается на родительские чанки (~2000 символов),
  каждый родитель — на мелкие перекрывающиеся дочерние чанки (~500 символов). Индексируются
  только дочерние (точность поиска), а LLM получает родителя целиком (полнота контекста).
- Строит dense-эмбеддинги дочерних чанков моделью `BAAI/bge-m3` и сохраняет их в ChromaDB
  с метрикой cosine + метаданными `parent_id`.
- Mapping «parent_id → текст» сохраняется в `chromadb/parent_map.json`.

**2. `retrieval.py`**
- Трёхканальный поиск:
  - Семантика: ближайшие чанки по косинусному сходству dense-эмбеддингов `BAAI/bge-m3` в ChromaDB.
  - Learned-лексика: SPLADE-подобный скоринг по sparse-весам BGE-M3 (`Σ q_i·d_i` по пересечению
    токенов) — ловит точные термины и имена.
  - Okapi BM25 на леммах (pymorphy3): точная лексика словоформ, дополняет learned-sparse.
- **Динамический top_k**: если `top_k` не задан явно, система оценивает сложность запроса
  (длина, вопросительные/сравнительные конструкции, число сущностей) и подставляет
  2-8 чанков: короткий фактоидный запрос → мало, многоаспектный → больше.
- Взвешенный Reciprocal Rank Fusion: `score(doc) = Σ w·1/(60 + rank)` по трём ранжированиям.
  Веса dense/sparse и фиксированный `top_k` (для автоподбора) система **подбирает сама**:
  `ingest.py`/`POST /reindex` считают отпечаток `data/*.txt` и, если документы изменились,
  запускают grid-search по eval-набору (`docs/eval_questions.json`), лучший конфиг сохраняется
  в `chromadb/retrieval_tuning.json`. Дефолты (dense 1.0, sparse 0.8, top_k 3) — эвристики.
  Ручной полный подбор — `python retrieval.py --tune`.
- **Parent-Child подстановка**: найденный дочерний чанк заменяется на родительский перед
  реранкингом, чтобы LLM видел полный контекст раздела.
- Опциональный реранкинг: кросс-энкодер `BAAI/bge-reranker-v2-m3` переоценивает
  кандидатов и возвращает точный топ-N.

**3. `agent.py`**
- **Декомпозиция запроса**: отдельный LLM-вызов разбивает сложный вопрос на 1-3 подзапроса
  (JSON-массив). Пример: «Каковы риски ЦДНГ и меры контроля?» → `["риски Цех добычи нефти и газа", "меры контроля ЦДНГ"]`.
- **Параллельный поиск**: подзапросы выполняются через `ThreadPoolExecutor`, контексты объединяются.
- **Синтез**: единый LLM-вызов без tool-calling формирует ответ по объединённому контексту.
- Защита от деградации: если декомпозиция не дала JSON — fallback на оригинальный запрос.
- Результат всегда дедуплицируется и сортируется; источники выводятся кодом, а не надеждой на модель.

**4. `main.py`**
- Интерактивный диалог в консоли; команды `/history`, `/clear`, `/quit`.
- История диалогов хранится в `history.json` между сессиями.

**5. `retrieval.py`**
- Eval-набор в `docs/eval_questions.json` (вопрос → ожидаемый источник).
- Recall@3 - доля вопросов, где нужный документ доставлен в топ-3; MRR@3 - качество
  ранжирования внутри топ-3; NDCG@5 - позиционно-взвешенная метрика на глубине 5.
- Метрики доступны в `--tune --metric {mrr|recall|ndcg}` — можно оптимизировать
  веса под любой критерий.
- Авто-подбор параметров: система сама переподбирает веса при изменении документов
  (`ingest.py`/`POST /reindex`); ручной полный прогон — `python retrieval.py --tune`.

**6. `sessions.py`**
- Персистентное хранилище диалогов на Redis (ключ `gpn:session:{id}`, список сообщений).
- TTL сессии — 24 часа (скользящее окно); `GET/DELETE /history` работают с Redis.
- Graceful degradation: если Redis недоступен — автоматический fallback на in-memory dict.

**7. `tracing.py`**
- Опциональная наблюдаемость через Langfuse (self-hosted).
- Каждый запрос — один трейс со спанами: `resolve_slang`, `query_decomposition`,
  `batch_search` (dense/sparse/bm25/rrf/rerank), `llm_synthesize`, `self_check`.
- Без `LANGFUSE_*` переменных все трейс-функции — no-op (0 добавленной латентности).

> **Про выбор `qwen2.5:14b`:** лучшее соотношение качества русского текста, надёжности tool-calling и скорости на CPU в рамках ограничений (open-модель ≤40B). Дефолтный тег — `q4_K_M` (~9 ГБ). На очень слабых машинах опуститесь до `qwen2.5:7b` или `llama3.2` — код без изменений, достаточно `LLM_MODEL=`.

Скорость: при старте модель прогревается (не грузится с нуля на первый запрос жюри), а `keep_alive=-1` держит её в памяти между запросами — второй и последующие ответы в разы быстрее. Декомпозиция: сложный запрос разбивается на несколько подзапросов, контекст и источники суммируются.

## Структура проекта
* `data/` - директория для текстовых документов и баз знаний.
* `corporate_dictionary.json` - корпоративный словарь аббревиатур и терминов.
* `core.py` - чистые функции (чанкинг, parent-child чанкинг, лемматизация, RRF, распознавание сленга, динамический top_k) без тяжёлых ML-зависимостей — их легко юнит-тестировать.
* `ingest.py` - скрипт загрузки, parent-child чанкинга и индексации в ChromaDB (dense-эмбеддинги BGE-M3).
* `agent.py` - логика агента: декомпозиция запроса, распознавание сленга, параллельный поиск, синтез.
* `retrieval.py` - модуль гибридного поиска на одной модели BGE-M3 (dense + sparse, взвешенный RRF), подстановка родителей, динамический top_k и оценка качества.
* `sessions.py` - персистентное хранилище диалогов на Redis (с in-memory fallback).
* `tracing.py` - опциональная наблюдаемость (Langfuse): трейс на запрос, спаны по шагам; no-op без конфигурации.
* `app.py` - HTTP API на FastAPI (эндпоинты `/chat`, `/history`, `/reindex`, `/health`).
* `main.py` - точка входа для запуска диалога с агентом в консоли.
* `tests/` - юнит-тесты (`pytest tests/`, 46 тестов).
* `docs/demo_cases.md` - сценарии для демонстрации жюри.
* `examples/` - готовые скрипты демо-прогона (`run_demo.sh`, `run_demo.ps1`).
* `.env.example` - шаблон переменных окружения (LLM, Redis, Langfuse).
* `Dockerfile`, `docker-compose.yml` - контейнерная сборка с предзагрузкой моделей, Ollama, Redis и Langfuse.
* `requirements.txt` - список зависимостей проекта.

## Корпоративный словарь

Словарь аббревиатур лежит в `corporate_dictionary.json` в формате `"аббревиатура": "расшифровка"`:

```json
{
  "ГПН": "Газпром нефть",
  "ГПНР": "Газпромнефть-Развитие"
}
```

- Если файла нет или он битый, агент использует встроенный fallback-словарь (`agent.py`) — прототип не падает.
- При запросе каждый токен нечетко сопоставляется с ключами словаря (`rapidfuzz`): точное написание не шумит, а «гпнр», «ГПН-Р», опечатки вроде `КПЕ → КПЭ` распознаются автоматически (для аббревиатур порог мягче — 60%, для обычных слов — 80%).
- Токен приводится к каноническому виду: убираются разделители («ГПН-Р» → ГПНР) и заменяются визуальные омонимы латиница/кириллица («ГПН» с латинской H → ГПН).
- Работает **двунаправленная карта**:
  - прямая: «АЗС (автозаправочная станция)» — аббревиатура в запросе дополняется расшифровкой;
  - обратная: пользователь пишет «автозаправочная станция», а в документах только «АЗС» → система по леммам находит расшифровку в запросе и дописывает «(АЗС)», чтобы лексический поиск гарантированно нашёл документ с аббревиатурой. Падежи («ключевыми показателями эффективности» → КПЭ) покрываются лемматизацией pymorphy3.
- Расшифровки подставляются в system-промт (блок `<resolved_slang>`) и обогащают запрос для поиска, поэтому LLM обязана их учитывать в ответе.

## Запуск

### Локально

```bash
pip install -r requirements.txt
python ingest.py            # построение базы знаний из /data
python main.py              # диалог с агентом в консоли
```

Требуется установленный и запущенный **Ollama** с загруженной моделью `qwen2.5:14b`:
```bash
ollama pull qwen2.5:14b
```

### Тесты

```bash
pip install -r requirements.txt
pytest tests/ -q   # 46 тестов: чанкинг, parent-child, лемматизация, RRF, распознавание сленга, динамический top_k
```

Тесты не скачивают ML-модели — они покрывают только чистые функции из `core.py`.

### Docker (рекомендуемый способ)

```bash
# обязательно: скопировать и заполнить переменные окружения
cp .env.example .env   # при желании — ключи Langfuse

docker compose up --build
```

Происходит автоматически:
1. Скачиваются HF-модели (эмбеддер + реранкер) и запекаются в образ.
2. Поднимается контейнер `ollama`, скачивается `qwen2.5:14b` (том `ollama_data`).
3. Поднимается `redis` (том `./redis-data`) — персистентное хранилище сессий.
4. Поднимается `langfuse` + `langfuse-db` (Postgres) — наблюдаемость; если ключи не заданы, трейсинг остаётся no-op и никак не влияет.
5. `ingest.py` строит базу знаний в ChromaDB (том `./chromadb`).
6. Стартует API на `http://localhost:8000`; Langfuse UI — на `http://localhost:3000`.

Повторные запуски быстрые: все модели уже в томах, база знаний не пересоздаётся.

Устойчивость: модели и база знаний инициализируются **лениво** — сервис не падает, если папки `./chromadb` ещё нет (на старте появится предупреждение, поиск вернёт пусто). Redis/Langfuse опциональны: если Redis недоступен, сессии живут в памяти; без Langfuse-ключей трейсинг — no-op. После добавления документов в `data/` достаточно `POST /reindex`, перезапуск не нужен.

## Оценка качества поиска

Оценка качества поиска проводилась на тестовом наборе запросов с фиксированной глубиной выдачи $K=3$:

| Метод поиска | Recall@3 | MRR@3
| :--- | :--- | :--- |
| **Семантический поиск** | 0.92 | 0.821
| **Гибридный поиск (без реранкера, без лемм)** | 1.00 | 0.859
| **Гибридный поиск + BGE-M3(без лемм))** | 0.92 | 0.923
| **Гибридный поиск (без реранкера + лемматизация)** | 1.00 | 0.795
| **Гибридный поиск + BGE-M3 + лемматизация)** | **1.00** | **1.000**

## Результаты реранкинга

>Мультиязычный реранкер (BGE-M3) улучшил MRR@3 с 0.859 до 0.923 (+7.5%), но снизил Recall@3 с 1.00 до 0.92.  
**Вероятная причина:** агрессивное переупорядочивание на запросах с неточными формулировками. Для работы в реальных условиях рекомендуется A/B-тестирование обоих реранкеров на реальных пользовательских запросах.

## Результаты лемматизации

>Лемматизация ухудшила качество ранжирования без реранкера (MRR 0.859 -> 0.795), скорее всего из-за того, что разные чанки стали выглядеть похоже после приведения к леммам. Реранкер компенсировал это ухудшение: пара (query, doc) видна ему целиком и результат не зависит от токенизации.  
**Итог:** лемматизация + реранкер - это лучший результат, но без реранкера лемматизацию лучше не использовать.

## Известные ограничения (Known Limitations)
**Декомпозиция зависит от качества LLM:** на малых моделях (3B) разбиение сложного вопроса иногда даёт нерелевантные подзапросы. Дефолт `qwen2.5:14b` заявлен как надёжный минимум; при ошибочном разбиении используется fallback на оригинальный запрос целиком.

**Parent-Child подстановка:** перед реранкингом дочерний чанк заменяется родительским, поэтому число источников в ответе может быть меньше `top_k` (родители дедуплицируются по `parent_id`).

## Roadmap

### Приоритетные

1. **Обработка ошибок в инструментах (graceful degradation)**: при недоступности поиска агент должен отвечать понятным сообщением, а не падать с 503.
2. **YAML-конфиг**: вынести параметры чанкинга, retrieval и моделей в отдельный файл.
3. **BM25-канал**: уже добавлен (третий канал fusion, см. раздел retrieval).
4. **Структурный + Parent-Child чанкинг**: уже добавлены — `adaptive_chunk` держит заголовки разделов, `parent_child_chunk` разбивает документ на родительские/дочерние чанки.
5. **Декомпозиция запроса**: уже добавлена — сложные вопросы разбиваются на подзапросы, которые ищутся параллельно.
6. **Динамический top_k**: уже добавлен — число чанков в контекст подбирается по сложности запроса.
7. **Redis-сессии и Langfuse-трейсинг**: уже добавлены — персистентные диалоги на Redis с in-memory fallback, наблюдаемость через Langfuse (no-op без ключей).

### Долгосрочные

8. **BGE-M3 multi-vector (ColBERT)**: включение третьего режима эмбеддингов для late-interaction скоринга — дальнейшее улучшение над текущим dense+sparse.
9. **Синонимы и query expansion**: расширение запроса синонимами отраслевых терминов (LambertW-механику уже покрывает словарь, но полноценный синонимический слой не реализован).
10. **NDCG@K с градацией релевантности**: сейчас NDCG@5 считается на бинарной релевантности (один источник на вопрос); при наличии многоуровневых эталонов (0–3) метрика станет полноценной.
